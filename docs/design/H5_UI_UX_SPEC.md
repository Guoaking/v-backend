# 考勤微应用前端 H5 设计规范 (UI/UX Design Spec)

## 1. 设计基调与核心理念 (Design Principles)

这是一个面向 B端客户员工（C端用户）的“即用即走”工具。设计必须遵循以下原则：
1. **极致克制 (Minimalism)**：不抢戏，不复杂。员工早高峰打卡是在奔跑中完成的，页面必须在 1 秒内加载，核心按钮必须大。
2. **信任感 (Trustworthiness)**：由于涉及采集敏感的人脸和证件信息，页面必须显得专业、合规、安全。
3. **容错性 (Forgiveness)**：网络差、光线暗、戴口罩等情况随时发生，失败提示必须温和，降级路径必须明显。

## 2. 页面一：新员工入职注册页 (Onboarding H5)

### 2.1 页面布局与视觉层级
这是一个“向导式 (Wizard)”页面，分为 3 个 Step，切忌把所有表单堆在一个长页面里。

- **全局配色**：干净的纯白背景 (`#FFFFFF`)，品牌主色（如信任蓝 `#2563EB`）作为按钮和高亮色，文字使用高对比度的深灰 (`#1E293B`)。
- **全局 Header**：顶部只显示企业 Logo（如果老板配置了）和一句温暖的欢迎语：“欢迎加入 [企业名称]”。

### 2.2 交互流程 (Steps)

#### Step 1: 证件采集 (ID Capture)
- **视觉焦点**：屏幕中央一个巨大的、带有圆角的虚线框，里面是一个“相机”Icon，下方文字：“点击拍摄证件正面”。
- **下方辅助区**：一个小号的下拉菜单，允许用户切换证件类型（默认选中“身份证”）。
- **交互细节**：点击后直接唤起系统相册/相机。上传时显示一个带有“骨架屏”扫描动画的 Loading 态，缓解 OCR 等待焦虑。

#### Step 2: 信息核对与纠错 (Human-in-the-loop)
- **视觉焦点**：表单设计。
  - **核心设计**：凡是 OCR 识别出来的字段，输入框的右侧都带有一个绿色的“✓”小图标，暗示系统已经帮你填好了。
  - **纠错引导**：在表单顶部加一句提示（微黄底色 warning 框）：“请核对以下信息，如有误请直接修改”。
- **底部悬浮 (Fixed Bottom)**：一个全宽的“下一步：录入人脸”按钮。

#### Step 3: 人脸录入与合规授权 (Face Enrollment & Compliance)
- **视觉焦点**：一个圆形的相机预览区域。下方文字：“请平视屏幕，保持光线充足”。
- **合规强制 (Critical)**：在最终的“提交注册”按钮上方，必须有一个 Checkbox。
  - `[ ] 我已阅读并同意《隐私与生物信息处理协议》`
  - 如果未勾选，提交按钮置灰（Disabled）。

## 3. 页面二：日常考勤打卡页 (Punch-in H5)

这是使用频次最高（每天2次）的页面。设计目标：**盲操可用**。

### 3.1 页面布局与视觉层级
- **首屏即核心**：不要让用户往下划。页面核心是一个巨大的圆形按钮（或直接是相机预览框）。
- **状态区**：顶部显示当前时间（大字号数字时钟动态跳动，如 `08:55:23`），以及当前的定位状态（如果开启了定位）。

### 3.2 交互流程 (Scenarios)

#### 场景 A：首次打卡 / 设备无缓存 (Identity Verification)
- 页面中央是一个简洁的输入框：“请输入手机号后4位”。
- 只要输入满 4 位，自动触发键盘收起，并在下方弹出一个“气泡”：
  - “你是：张*明 吗？” -> 点击确认 -> 进入刷脸。
  - 这种渐进式的信息展现比直接弹出一个大列表更有安全感。

#### 场景 B：日常极速打卡 (Device Trust - Happy Path)
- **视觉冲击**：页面一打开，中央就是一个巨大的蓝色渐变呼吸光圈，里面显示实时摄像头画面。
- **个性化问候**：光圈上方大字显示：“早上好，张明！”。
- **一键操作**：光圈下方是一个巨大的按钮：【立即刷脸打卡】。
- **安全逃生舱**：在最底部有一行很淡的灰色小字：“我不是张明，切换身份”。

#### 场景 C：识别失败与降级 (Fallback Mode)
- **交互逻辑**：如果连续 2 次活体或比对失败（返回 `400/401`），**立刻停止重试**。
- **视觉突变**：页面主色调从蓝色变为温和的橙色（警告色，切忌用红色报错吓唬员工）。
- **降级文案**：“环境光线不佳，无法识别。请直接拍摄现场照片完成打卡”。
- **操作变更**：此时调用的不再是活体组件，而是普通的 `<input type="file" capture="camera">`，拍完直接提交，提示“打卡已记录，等待 HR 复核”。

## 4. 前端工程实施建议 (Technical Directives for Frontend)

1. **分离部署**：
   建议这两个 H5 页面（`/enroll` 和 `/punch`）做成轻量级的 SPA（单页应用），甚至直接用 Vanilla JS 或极简的 Preact/Vue 编写，不要把庞大的 B端 Console 依赖打包进去，确保秒开。
2. **状态机管理 (State Machine)**：
   打卡页是一个典型的状态机：`[Init] -> [Identity_Check] -> [Camera_Ready] -> [Liveness_Checking] -> [Success / Fallback]`。前端代码应当严格按照状态机来写，避免回调地狱。
3. **Magic Link 提取**：
   在应用的入口 `main.js` 中，第一时间解析 URL 里的 `?token=xxx`，并将其存入 `sessionStorage`。然后为所有 Axios/Fetch 请求配置统一的拦截器，注入 `Authorization: Bearer <token>`。
